## v1과 뭐가 다른가

v1은 `pem_model.py`를 서버 프로세스 안에서 직접 돌렸습니다. 이 파일은
`RE_REGION_NAME`, `J_MAX` 같은 값을 "모듈 전역변수"로 두고 여러 함수가 직접
참조하는 구조라서, 요청 두 개가 동시에 들어와 지역이 다르면 전역변수가 서로
덮어써져서 결과가 섞일 위험이 있었습니다. 그래서 v1은 `COMPUTE_LOCK` 하나로
계산 전체를 직렬화해서 "한 번에 한 명씩만" 계산하게 막아뒀습니다.

v2는 매 요청마다 `pem_model.py`를 **완전히 새로운 파이썬 프로세스**(`worker.py`)
에서 돌립니다. 프로세스가 다르면 메모리도 완전히 분리되니 전역변수가 절대
섞이지 않습니다 — Lock이 필요 없어지고, 여러 요청을 동시에 안전하게 처리할 수
있습니다. 대신 매번 새 프로세스를 띄우는 비용(파이썬/numpy/pandas 재로딩,
1~2초)이 추가로 듭니다.

로컬 테스트 결과: 지역이 다른 요청 2개를 정확히 동시에 보내도 각자 자기
지역의 정확한 결과를 받았고(섞임 없음), 전체 걸린 시간도 한 번만 돌릴 때와
거의 같았습니다(순차 실행이 아니라 진짜 병렬 실행됨을 확인). 5개를 동시에
보냈을 때도 앞 2개는 즉시 실행되고 나머지 3개는 "대기 중(앞에 N명)"으로
정확한 순서를 보여주며 기다렸다가 에러 없이 모두 정상 완료됐습니다.

## "몇 명이 몰려도" 안전하게 만든 두 번째 개선 — 작업 큐 + 진행 상황 표시

처음 버전은 브라우저가 `/api/run` 요청 하나를 계산이 끝날 때까지 계속 붙들고
있는 방식이었습니다. 이러면 대기줄이 길어질 때(예: 5~10명이 몰려서 뒷사람이
몇 분을 기다려야 하는 상황) 그 긴 시간 동안 브라우저 요청이 열려있게 되고,
결국 gunicorn이나 Render 자체의 타임아웃에 걸려 "오류"처럼 보이는 실패가 날
위험이 있었습니다.

그래서 지금은 이렇게 바꿨습니다:

1. "확인" 버튼 → `/api/run`은 계산을 큐에 등록만 하고 `job_id`를 즉시 돌려줍니다
   (0.1초도 안 걸림).
2. 브라우저가 `/api/status/<job_id>`를 1.2초마다 확인(polling)해서 화면에
   "대기 중입니다 (앞에 N명)" → "계산 중입니다..." → 완료 시 결과 표시,
   순서대로 보여줍니다.
3. 실제 계산은 서버가 미리 띄워둔 백그라운드 워커 스레드들(`MAX_CONCURRENT_JOBS`개)이
   큐에서 하나씩 꺼내서 처리합니다.

이렇게 하면 브라우저의 개별 HTTP 요청은 항상 순식간에 끝나기 때문에, 대기줄이
얼마나 길어지든(사람이 몇 명이 몰리든) 타임아웃으로 실패할 일이 없습니다.
실제로 동시에 계산이 도는 개수(`MAX_CONCURRENT_JOBS`, 메모리 보호용)는
그대로지만, 그 이상 온 사람은 에러 없이 화면에 정확한 대기 순서를 보면서
기다리기만 합니다. 로컬에서 5명 동시 접속을 시뮬레이션해서 대기 순서 표시와
최종 결과가 모두 정확함을 확인했습니다.

**주의**: 이 작업 큐는 파이썬 프로세스 메모리 안에만 존재하므로, gunicorn을
반드시 `--workers 1`로 유지해야 합니다 (Procfile에 이미 그렇게 되어 있음).
`--workers`를 2 이상으로 늘리면 요청이 서로 다른 프로세스로 나뉘어 큐/대기
상태가 공유되지 않아 오작동합니다 — 동시 처리량은 `MAX_CONCURRENT_JOBS`와
`--threads` 값으로 조절하세요.

## 동시 실행 개수 제한 (`MAX_CONCURRENT_JOBS`)

Render 무료 플랜은 메모리가 512MB로 넉넉하지 않습니다. 계산 프로세스 하나가
numpy/pandas를 새로 불러오고 8,760시간짜리 배열을 3케이스만큼 들고 있어야 해서,
너무 많은 프로세스가 동시에 뜨면 메모리 부족(OOM)으로 서비스 전체가 죽을 수
있습니다. 그래서 기본값 2로 제한해뒀습니다 (Render Environment 탭에서
`MAX_CONCURRENT_JOBS` 환경변수를 추가하면 조정 가능).

**대회 전에 꼭 해볼 것**: 실제로 2~3대의 폰(또는 컴퓨터)으로 동시에 확인
버튼을 눌러보고, Render 대시보드의 로그에 메모리 부족 관련 에러(예: 프로세스가
갑자기 죽거나 "Out of memory")가 없는지 확인하세요. 문제가 없으면
`MAX_CONCURRENT_JOBS`를 3으로 올려서 다시 테스트해도 됩니다. 문제가 생기면
2로 유지하거나 1로 낮추세요 (1로 낮추면 v1과 비슷하게 순차 처리되지만, 그래도
Lock 방식보다 구조적으로 더 안전합니다).

## 배포 방법 (v1과 동일하되, 완전히 새 서비스로)

1. 이 폴더를 **v1과는 다른 새 GitHub 저장소**(또는 같은 저장소의 다른 폴더)에
   올립니다. v1 저장소를 덮어쓰지 마세요.
2. Render에서 **New + → Web Service**로 새 서비스를 만듭니다 (v1 서비스는
   그대로 둠).
3. Root Directory를 이 폴더 경로로 지정 (폴더째로 올렸다면).
4. Environment 탭에서 `PYTHON_VERSION = 3.11.9` 추가 (v1에서 겪었던 pandas
   빌드 에러 방지 — `.python-version` 파일도 넣어뒀지만 확실하게 하려면 둘 다
   해두는 게 안전).
5. Build Command: `pip install -r requirements.txt`
6. Start Command: `gunicorn app:app --worker-class gthread --workers 1 --threads 6 --timeout 170 --bind 0.0.0.0:$PORT`
   (Procfile에 이미 적혀있어서 자동 인식될 수도 있음)
7. Create Web Service → 새 주소(`https://<새이름>.onrender.com`)가 생기면
   그 주소로 동시 접속 테스트를 해봅니다.

풍력 데이터 제약(5개 지역만, 2023년 기준)이나 화면 구성은 v1과 완전히 동일합니다.

방식 등)는 그대로 유지돼 있어서 큰 수정 없이 붙일 수 있었다. 바뀐 점 요약:

- **핵심 개선**: LCOH 계산이 "1년치 스냅샷"에서 "20년 수명주기 DCF"로 바뀌었다.
  PEM 스택 열화(Su et al. 2024 커널)를 반영해서 해마다 스택 성능이 떨어지고,
  수명(전압 EOL 기준)에 도달하면 교체 비용이 들어가는 걸 전부 현재가치로
  할인해서 LCOH에 반영한다. 촉매 모델은 IrO2 고정으로 단순화됐다(기존엔 여러
  촉매 중 선택 가능했는데, 이 웹앱에선 원래도 촉매 선택 기능을 안 썼어서 영향 없음).
- **worker.py 수정 필요했던 부분**: `main()` 시그니처에서 `run_hysteresis` 인자가
  없어져서 호출부에서 뺐다.
- **build_payload.py 수정 필요했던 부분**: LCOH 항목 키 하나가
  `annualized_capex` → `capex`로 이름이 바뀌어서(20년 DCF 기준으로 의미가 살짝
  달라짐) 화면 표시용 한글 라벨을 추가했다.
- **성능 버그 발견 및 수정 (중요)**: 새 모델을 그대로 붙였더니 계산 1건에
  118초가 걸렸다(구모델은 로컬 7~13초). 원인을 추적해보니 거의 전부(105초)가
  Case 3(하이브리드 ESS) 최적점 탐색 하나에서 나왔다. Case 3는 전류밀도×ESS
  용량 조합 180개를 하나하나 실제로 돌려보면서 최적점을 찾는데, 그중 극히
  일부 조합에서 ESS 용량이 물리적으로 무의미할 만큼 작게(P*의 0.05시간
  미만) 산정되면 `dispatch_case3()`의 시간별 이벤트 루프가 한 시간 안에서
  수십만 번씩 완충/완방전을 반복하는 병리적 경우가 생겼다(실측: 한 grid
  point에서만 43초). 이런 후보는 ESS 왕복손실·재기동 비용 때문에 애초에
  최적점이 될 수 없으므로, `find_operating_point_case3`와 `_size_ess`에
  최소 용량 하한(P*의 0.05시간)을 추가해서 dispatch를 돌리기 전에 걸러내도록
  고쳤다. **이 기준을 적용해도 최종 선택되는 최적 조합과 LCOH 값은 완전히
  동일함을 확인했다** — 정확도 손실 없이 계산시간만 118초 → 약 20~25초로
  줄었다(로컬 기준, 강원/전남/충남/제주 등 여러 지역·연도에서 재확인).
- **WORKER_TIMEOUT_S 조정**: 구모델 기준 Render 무료 플랜에서 로컬 대비
  5~8배 느렸던 걸 감안하면, 새 모델(로컬 20~25초)은 Render에서 대략
  110~200초까지 걸릴 수 있다고 보고 여유를 더 둬서 150초 → 240초로 올렸다.
  **실측 확인(2026-09, 실제 배포):** Render 무료 플랜에서 한 건에 **약 2분
  30초(150초)** 걸림 — 예상 범위(110~200초) 안이고 로컬 대비 약 6.8배로, 구모델
  때 관찰했던 5~8배 배율과 일치한다. 240초 타임아웃 안에 여유 있게 끝나서
  타임아웃으로 실패할 걱정은 없다. 다만 대회 당일 여러 명이 몰릴 때 대기시간에
  직접 영향을 준다: `MAX_CONCURRENT_JOBS=2`(기본값) 기준으로 뒤에서 N번째로
  줄 선 사람은 대략 `ceil(N/2) x 150초`를 기다리게 된다(예: 5번째 사람 ≈
  3번째 배치 ≈ 7.5분, 10번째 사람 ≈ 12.5분). 대기줄이 길어질 것 같으면
  `MAX_CONCURRENT_JOBS`를 3으로 올려보거나(Render 무료 플랜 메모리 한도
  512MB 내에서 버티는지 로그로 확인 필요), Render 유료 플랜으로 올려서
  150초 자체를 줄이는 쪽이 더 근본적인 해결책이다.
- **새로 발견된 데이터 참고사항**: 새 모델의 데이터 로더가 예상 시간 수(8,760h
  /윤년 8,784h)와 실제 로드된 시간 수를 대조해서 다르면 경고를 찍어주는데,
  이걸로 확인해보니 **풍력 2023년 데이터는 5개 승인 지역(강원·경남·경북·전남·
  전북) 전부 12월 데이터가 통째로 빠져있다**(8,760h 중 8,016h만 존재, 정확히
  744시간 = 12월 전체). 연간 이용률·경제성 계산 자체는 문제없이 돌아가지만,
  월별 발전량 차트에서 12월이 0으로 보일 수 있다는 점은 참고할 것. 태양광은
  2023/2024/2025 모두 이 문제가 없음을 확인했다.
